# Staging refresh from production (masked)

A super admin replaces the **staging** database with a **masked copy of
production** from the staging admin panel (Sistem → Test Araçları). The heavy
lifting runs in the GitHub workflow `.github/workflows/staging-refresh-from-prod.yml`
on the Coolify host; the production dump never leaves that server.

Part 1 is the shared contract (verbatim; the admin UI is built against it).
Part 2 explains how it works, what is masked, the secrets, and the runbook.

---

## Part 1 — Contract

Owner decisions (2026-10-09):

- A super admin presses ONE button in the STAGING admin panel (Sistem → Test Araçları) to replace the staging database with a masked copy of production. Hidden and refused on production.
- The heavy lifting runs in a GitHub Actions workflow (production DB credentials stay in GitHub secrets; the staging API container never gets them). The admin button triggers that workflow through the GitHub API and shows its progress/result.
- Personal data is masked deterministically (same production user → same fake identity on every refresh). Fake addresses use a non-deliverable domain (`uat.invalid`) so no mail can reach a real person. Password hashes, 2FA secrets, refresh tokens, sessions, OAuth links, verification tokens are wiped.
- The fixed UAT accounts (apps/api/prisma/data/uat/accounts.json: nur@, serhat@ members; tarodan@, developers@ super admins) are re-applied on top after every refresh with `UAT_SEED_PASSWORD`, using the existing UAT seed code (reuse, do not duplicate). Their starter listings are NOT re-created on a refresh (production listings exist).
- Images: staging reads production images read-only (whatever absolute/public URLs the rows carry keep working); new uploads on staging keep going to the staging S3 prefix. Nothing is ever written to the production prefix.
- PayTR merchant_oids, eLogo invoice numbers, order/trade numbers stay as in production.
- After the refresh staging is a normal working environment again (registration, orders, PayTR test, cargo simulation, mail routing). Everything testers created since the last refresh is deleted by the next refresh (the button says so and asks for confirmation).

### Status record (shared shape) — `packages/types/src/uat-refresh.ts`, exported from the package index

```ts
export const UAT_REFRESH_STATES = [
  "queued",
  "running",
  "succeeded",
  "failed",
] as const;
export type UatRefreshState = (typeof UAT_REFRESH_STATES)[number];

export interface UatRefreshMaskedCount {
  table: string;
  rows: number;
}

export interface UatRefreshRun {
  id: string; // our row id
  state: UatRefreshState;
  requestedBy: { id: string; displayName: string } | null; // null = started from GitHub directly
  requestedAt: string; // ISO
  startedAt: string | null;
  finishedAt: string | null;
  workflowRunUrl: string | null; // GitHub run html_url
  sourceSnapshotAt: string | null; // when the production dump was taken
  dryRun: boolean;
  masked: UatRefreshMaskedCount[]; // per table, filled by the workflow at the end
  migrationsApplied: string[]; // staging migrations newer than production that were applied after the import
  backupFile: string | null; // staging pre-refresh backup file name on the server
  error: string | null;
}

export interface UatRefreshStatus {
  available: boolean; // false on production or when the GitHub trigger is not configured
  unavailableReason: "production" | "notConfigured" | null;
  current: UatRefreshRun | null; // a queued/running run, if any
  last: UatRefreshRun | null; // latest finished run
  history: UatRefreshRun[]; // last 10, newest first
}
```

### Admin endpoints (super_admin only; return 404/403 on production — use the existing `isLiveProduction()` helper)

- `GET  /admin/test-tools/uat-refresh` → `UatRefreshStatus`
- `POST /admin/test-tools/uat-refresh` body `{ confirm: "STAGING"; dryRun?: boolean }` → `UatRefreshRun` (409 if one is queued/running; 503 with `server.uatRefresh.notConfigured` if the GitHub trigger env is missing)

### Workflow → API callback (machine-to-machine)

- `POST /internal/uat-refresh/:runId/report` with header `x-uat-refresh-token: <token>`, body `{ state: "running" | "succeeded" | "failed"; startedAt?; finishedAt?; sourceSnapshotAt?; masked?; migrationsApplied?; backupFile?; error?; workflowRunUrl? }`. The token is a per-run random secret generated by the API when it dispatches the workflow, stored hashed, passed to the workflow as a dispatch input, and valid only for that run. Not guarded by admin JWT. Rate-limited.
- Because the refresh REPLACES the staging database, the `uat_refresh_runs` table is wiped by the import. The workflow must therefore (a) export the current run's row and the run history before the import and re-insert them after migrations (simplest: the workflow calls the report endpoint after the API is back; the API upserts the row from the full payload it receives), so the history survives refreshes. Design this explicitly.

### i18n

- API agent: `server.uatRefresh.*`
- Admin agent: `admin.system.testTools.uatRefresh.*`

### Flow

```
admin "Refresh" (types STAGING)
  └─ POST /admin/test-tools/uat-refresh
       ├─ advisory lock; 409 if a run is queued/running (not timed out)
       ├─ uat_refresh_runs row: queued, token_hash = sha256(token)
       └─ GitHub workflow_dispatch (ref GITHUB_DISPATCH_REF) inputs:
            run_id, report_token (plain, 64 hex), dry_run, confirm=STAGING
workflow (SSH on the Coolify host)
  discover → guards → report running (+ workflow run link)
  → [dry run: size estimate + migration preview → report succeeded]
  → pg_dump -Fc production (host temp file, 600)
  → CREATE DATABASE <staging>_uat_scratch on the STAGING postgres, pg_restore, delete dump
  → prisma migrate deploy on scratch      (= migrationsApplied)
  → mask-database.js on scratch            (= masked, sourceSnapshotAt)
  → mask-database.js --verify + e-mail domain sample
  → seed-uat.js --accounts-only on scratch
  → pg_dump staging → ~/tarodan-staging-backups/staging-pre-refresh-<ts>.sql.gz (= backupFile)
  → carry staging rows into scratch: uat_refresh_runs, mail_sender_accounts, mail_area_settings
  → stop api, rename staging → <staging>_pre_refresh, scratch → staging, start api
       (unhealthy → automatic rollback to the previous database)
  → Redis flushdb, restart api (repeatable jobs + search reindex), drop <staging>_pre_refresh
  → report succeeded
any failure → trap: rollback if mid-swap, drop scratch, delete dump, restart api, report failed
```

Migrations run **before** masking on purpose: the catalogue describes the
staging schema, so the copy is brought to that schema first. If production has
a migration the staging image does not know (production ahead of staging), the
workflow refuses before dumping: a column the staging code does not know is a
column the catalogue does not cover.

### Run history across the swap (contract "design this explicitly")

Option (a), done with a table copy rather than an upsert:

1. The run row exists in the **live** staging DB from the start (the API creates
   it, or the workflow inserts it for a manual start).
2. The masking catalogue deletes production's `uat_refresh_runs` rows (production
   never has any) in the scratch DB.
3. Right before the swap the workflow `pg_dump --data-only`s `uat_refresh_runs`
   from the live staging DB and loads it into the scratch DB (after
   `TRUNCATE`). The current run (state `running`) and all history move with it,
   including the token hash.
4. After the API is back on the swapped DB, the workflow sends the final report
   with the **full** payload (startedAt, finishedAt, sourceSnapshotAt, masked,
   migrationsApplied, backupFile). The API authenticates it against the carried
   token hash and updates the row.

The table has no FK to `users`: the requester's user row may not exist after the
swap, so `requested_by_name` keeps a snapshot of the name. The report endpoint
updates; it does not create rows (it cannot authenticate a run it has never
seen) — the carry-over is what guarantees the row exists.

The same carry-over keeps staging's **own** mail routing (`mail_sender_accounts`
encrypted with the staging `MAIL_ACCOUNT_ENCRYPTION_KEY`, `mail_area_settings`),
so "mail routing works after the refresh" without ever holding production's
mailbox passwords.

### Manual start (from GitHub, `run_id` empty)

The workflow generates a UUID and a 64-hex token, inserts
`uat_refresh_runs (state queued, requested_by NULL, token_hash = sha256(token))`
into the live staging DB, then reports exactly like an API-started run. The
digest must stay identical to `hashReportToken` (SHA-256 hex of the UTF-8
token; spec-pinned). Such runs show `requestedBy: null`.

### API behaviour

- `GET` on production → `{ available: false, unavailableReason: "production", history: [] }`
  (200, so the panel can hide the card; nothing about runs is revealed).
  Without the trigger env → `available: false, unavailableReason: "notConfigured"`
  with history.
- `POST` on production → 403 `server.uatRefresh.productionRefused`; no trigger env →
  503 `server.uatRefresh.notConfigured`; active run → 409
  `server.uatRefresh.alreadyRunning`; GitHub refuses → the run is marked failed
  and the API answers 502 `server.uatRefresh.dispatchFailed`. Audit log action
  `uat_refresh_start`.
- Report endpoint: production → 404; unknown run or wrong token → the same 403
  `server.uatRefresh.invalidToken`; finished run → 409
  `server.uatRefresh.alreadyFinished`; throttled to 20/min.
- A run still `queued`/`running` 90 minutes after it was requested is returned as
  `failed` with `error: "timedOut"` (`UAT_REFRESH_TIMED_OUT_ERROR`; the panel
  translates the code) and no longer blocks a new run. The row is not rewritten:
  a late report from the workflow still wins. The workflow's job timeout is 85
  minutes, so a run the API shows as timed out cannot still be working.
- The workflow link comes from the workflow itself
  (`server_url/repository/actions/runs/run_id`) in the first report; the API does
  not poll the GitHub runs list.

### Images and storage

Rows keep the URLs/keys they had in production. Public images are absolute URLs
and stay readable. Private objects (seller documents, invoices, message
attachments) are presigned by key, and StorageService prefixes any key that is
not under its own env prefix with its own prefix — so staging cannot read
production's private objects (they show as missing). Writes always build the key
from the own prefix, and `deleteFileByKey` now refuses keys outside the own
prefix (the row is still removed). The workflow refuses a staging api whose
`S3_ENV_PREFIX` is unset (it would fall back to `prod`) or `prod`.

## Masking catalogue

Source of truth: `masking-catalog.ts`. Every rule has a reason in code. Fakes are
derived from the row key (default `id`), never from the real value.

**Fake formats.** e-mail `u<12 hex>@uat.invalid` · phone `+90500<7 digits>`
(valid `TR_PHONE_E164`, unassigned operator code) · TCKN 11 digits passing the
checksum · VKN 10 digits · IBAN `TR` + valid mod-97 check digits · first/last
names from fixed Turkish lists (full name = first + last of the same key) ·
street `UAT <name> Sokak No:n D:m` · company `UAT Firma <8 hex>` · username
`uat_<10 hex>` · birth date 1960–2000 · file name `document-<8 hex>.<ext>`.

**Messages (decision).** Marketplace/trade/support message text is kept so
testers see realistic conversations; e-mail addresses, TR mobile numbers, TR
IBANs and checksum-valid TCKNs inside the text are replaced. Names typed inside
free text are NOT detected (no reliable pattern); attachments are private
objects staging cannot read.

**JSON (decision).** Every JSON column is either scrubbed or on the reasoned
allow-list (settings, rule/tariff/policy snapshots, money breakdowns, labels).
The scrubber walks the value: keys that name personal data (`fullName`,
`guestEmail`, `user_phone`, `iban`, `tcKimlikNo`, `recipientVknTckn`,
`address`, `zipCode`, `ip`, `*token*`, `password` …) get a fake or `null`; every
other string goes through the free-text scrubber; shape and non-personal keys
(`city`, `district`, `*AddressId`, amounts, plain `name`) are untouched.

**Kept as is (owner decision).** Order/trade/package numbers, PayTR
merchant_oids, eLogo invoice numbers/ETTN, amounts, product data, public image
URLs, ratings, `users.bio`/avatars (already public), tax office, city/district.

**Allow-list.** `UAT_MASK_ALLOW_LIST` lists the columns whose name looks personal
but are not (flags, timestamps, address FKs, the platform's own merchant IBAN,
admin-authored campaign mails) and JSON columns without personal data — each
with a reason.

**Completeness guard.** `masking-catalog.contract.spec.ts` parses
`schema.prisma`; it fails when a column whose Prisma field name matches
`email|phone|iban|nationalId|tckn|address|fullName|firstName|lastName|birthDate|password|secret|token`
(or `ip` as a camelCase word), or any `Json` column, has neither a rule nor an
allow-list entry. It also fails on catalogue entries that no longer exist,
`NULL` rules on non-nullable columns, type mismatches, unique columns using
original-dependent fakes, and stale allow-list rows. Adding a personal column
means adding a rule (or a reasoned allow-list line) in the same change.

### Runner guarantees

- Refuses unless `UAT_MASK_TARGET=scratch`, the database name ends with
  `_uat_scratch`, `UAT_MASK_FORBIDDEN_DATABASE_URL` (production host + name, **no
  credentials**) is given and its name differs, and the process is not a live
  deployment. Errors never print the password.
- Set-based: `NULL`/constant columns in one `UPDATE`; computed columns read in
  primary-key pages of 1000 and written with one
  `UPDATE … FROM unnest(ids, values)` per column per page; unique columns are
  first parked on `'__uat_tmp__' || ctid` so a fake can only collide with another
  fake, which is resolved with an attempt counter.
- User triggers on the touched tables (consent/identity/ledger append-only
  guards, test-lane stamps, finalized refund policy) are disabled **by name** for
  the run and re-enabled in `finally`; verification fails if any stays disabled.
- Idempotent: fakes depend on the row key only, the scrubbers are fixed points.
- Verifies (queries derived from the catalogue): deleted tables empty, NULL
  columns empty, e-mail columns only `@uat.invalid` (system rows excepted),
  phone columns only `+90500…`. Prints `{"masked":[{table,rows}],"sourceSnapshotAt":…}`
  as the last stdout line. `--check` = guard only, `--verify` = verification only.

| Name                                                | Where                         | Notes                                                                                                                                                                                         |
| --------------------------------------------------- | ----------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GITHUB_DISPATCH_TOKEN`                             | **staging** api env (Coolify) | Fine-grained PAT (or GitHub App token) for this repository only, permission **Actions: Read and write**. Optional: absent → button "not configured". Refused at boot on `APP_ENV=production`. |
| `GITHUB_DISPATCH_REPO`                              | staging api env               | `owner/repo`, e.g. `sigmoida/tarodan-app`. Must be set together with the token.                                                                                                               |
| `GITHUB_DISPATCH_REF`                               | staging api env (optional)    | Branch the workflow runs from; default `development`. The workflow file must exist on that branch.                                                                                            |
| `SERVER_HOST`, `SERVER_USERNAME`, `SERVER_PASSWORD` | GitHub secrets (existing)     | SSH into the Coolify host.                                                                                                                                                                    |
| `COOLIFY_STAGING_UUIDS`                             | GitHub secret (existing)      | First field = staging api app UUID.                                                                                                                                                           |
| `COOLIFY_PROD_UUIDS`                                | GitHub secret (existing)      | First field = production api app UUID. Must be visible to the `staging` environment (repository-level secret, or add it to that environment).                                                 |
| `UAT_SEED_PASSWORD`                                 | GitHub secret (existing)      | Password of the re-applied fixed accounts.                                                                                                                                                    |

No new production credential is stored anywhere: the workflow reads the
production `DATABASE_URL` from the production api container on the host, as
`production-reset.yml` does, and only passes host + database name (no password)
to the staging container. Passwords reach `psql`/`pg_dump` via `docker exec -e
PGPASSWORD` (copied from the shell, never on a command line) and are never
printed. The report token is masked in the logs (`::add-mask::`).

Note: `workflow_dispatch` inputs are visible to people with read access to the
repository's Actions. The report token only authorises reports for its own run
while that run is unfinished; after the run ends it is useless.

## Runbook

**Before the first run**

1. Deploy staging from a commit that contains this feature (the migration,
   `dist-seed/prisma/uat/mask-database.js`, `seed-uat.js --accounts-only`).
   Production must not be ahead of staging in migrations (the workflow checks).
2. Set `GITHUB_DISPATCH_TOKEN` + `GITHUB_DISPATCH_REPO` (+ optionally
   `GITHUB_DISPATCH_REF`) on the staging api and redeploy/restart it.
3. Make sure `COOLIFY_PROD_UUIDS` is visible to the `staging` environment.
4. Check staging's `S3_ENV_PREFIX` is `staging` (the workflow refuses unset/`prod`).
5. Check staging integrations are in test mode (PayTR test merchant, Sürat test,
   eLogo demo, `PAYOUTS_DISABLED`): staging now holds production orders, and
   its crons will act on them against whatever endpoints staging is configured
   for.

**Dry run first (always)**

- Panel: Sistem → Test Araçları → "Refresh from production" → dry run; or
  GitHub → Actions → **Staging Refresh From Production** → `confirm=STAGING`,
  `dry_run` ticked.
- It discovers both api/postgres containers, runs every guard, both
  pre-flights (`seed-uat.js --check`, `mask-database.js --check`), the
  migration comparison and prints the production DB size against free disk.
  Only metadata is read from production (applied migrations, database size);
  nothing is copied, and nothing is written except the run row.

**Real run**

- Same button without dry run (or the workflow with `dry_run` unticked). Expect
  minutes to tens of minutes depending on the production size. Staging keeps
  serving until the swap; the api is down for the swap and two restarts
  (~1–3 minutes). Listings become searchable ~5 minutes after the last restart.
- Everything testers created on staging since the last refresh/reset is gone;
  the pre-refresh backup is
  `~/tarodan-staging-backups/staging-pre-refresh-<UTC ts>.sql.gz` (last 5 kept,
  shared rotation with Staging Reset).
- Afterwards: fixed UAT accounts log in with `UAT_SEED_PASSWORD`; production
  people exist with masked identities and **no password** (they cannot log in).

**If it fails**

- Before the swap: staging is untouched; the scratch DB and the dump are
  removed by the trap. Read the phase in the run's `error`.
- During/after the swap, before success: the trap renames the previous database
  back and restarts the api automatically.
- If the rollback itself fails, the log names the databases
  (`<db>`, `<db>_pre_refresh`, `<db>_failed_refresh`). Manual recovery on the
  host: stop the staging api, `ALTER DATABASE "<db>_pre_refresh" RENAME TO "<db>"`
  (after renaming/dropping a broken `<db>`), start the api. Last resort: restore
  the `.sql.gz` backup into an empty `<db>` with `gunzip -c … | psql`.
- A leftover dump file can only exist if the host died mid-run:
  `~/tarodan-uat-refresh/production-*.dump` — delete it.

## What could not be verified here

Written without running anything (no Docker, no database, no GitHub run). Before
relying on it, the dry run and one real run on staging must confirm:

- The staging postgres user can `CREATE`/`DROP`/`ALTER DATABASE … RENAME` and owns
  the restored tables (needed to toggle triggers); `template1` is reachable.
- `pg_restore --no-owner --no-acl --no-comments --exit-on-error` restores the
  production dump cleanly (extensions such as `pg_trgm` must be creatable).
- `prisma migrate deploy` behaves on the restored copy as expected.
- Coolify does not restart the api on its own while it is stopped for the swap,
  and the postgres healthcheck tolerates the database being renamed for a moment.
- The ssh-action remote shell runs the script as written (it is POSIX and was
  syntax-checked with `bash -n` and `dash -n`).
- Runtime of the masking on production-sized tables (indexes on masked columns
  are updated row by row by PostgreSQL; large `audit_logs`/`orders` tables are
  rewritten once per JSON column).
- Whether `workflow_dispatch` inputs (the report token) are shown in the GitHub
  UI for this repository.

Known limitations: names typed into free text are not detected; staging's
Elasticsearch indices and Next caches catch up on their own (periodic search
sync; page caches expire) rather than being rebuilt explicitly.
