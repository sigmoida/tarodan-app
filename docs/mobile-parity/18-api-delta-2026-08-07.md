## 1. Checkout komisyon snapshot'ı ⚠️ KIRICI / P0

`POST /orders/quote` yanıtında iki yeni zorunlu snapshot alanı ve satır bazlı
uygunsuzluk listesi vardır:

```jsonc
{
  "commissionRuleSetId": "uuid",
  "commissionRuleSetVersion": 7,
  "shippingTariffVersion": 4,
  "pricingHash": "16-char-hash",
  "items": [/* gerçekten fiyatlanan satırlar */],
  "unavailableItems": [
    {
      "productId": "uuid",
      "sellerId": "uuid", // ürün bulunduysa
      "code": "SELLER_SALES_SUSPENDED",
      "message": "...",
    },
  ],
}
```

`unavailableItems[].code`:

- `PRODUCT_NOT_FOUND`: ürün yok veya yalnız ödeme amaçlı sanal ürün.
- `PRODUCT_NOT_ACTIVE`: ilan artık satışta değil.
- `SELLER_SALES_SUSPENDED`: kurumsal satıcının satış yetkisi/üyeliği geçerli değil.

Quote **200 ile kısmi başarı** dönebilir: `items[]` yalnız fiyatlanan satırlardır,
`unavailableItems[]` dışarıda bırakılan satırlardır. Mobil:

1. İstenen ürün ID'leri ile `items[]`/`unavailableItems[]` kapsamını karşılaştırmalı.
2. Uygun olmayan satırları ödeme özetinden çıkarmalı, kullanıcıya gerekçeyi göstermeli
   ve sepeti yeniden çekmeli.
3. Sunucunun döndürdüğü `pricing.summary` ve `totalAmount` değerlerini göstermeli;
   çıkarılan satırlardan istemcide yeniden toplam üretmemeli.

Aşağıdaki dört sipariş oluşturma gövdesine quote'tan gelen alanlar **aynen** eklenir:

- `POST /orders/checkout`
- `POST /orders/checkout/guest`
- `POST /orders/buy`
- `POST /orders/guest`

```jsonc
{
  "expectedShippingTariffVersion": 4,
  "expectedCommissionRuleSetId": "uuid",
  "expectedCommissionRuleSetVersion": 7,
  "expectedPricingHash": "16-char-hash",
}
```

Kurallar:

- ID/sürüm eksik veya geçersizse istek DTO doğrulamasında reddedilir.
- Aktif komisyon seti quote'tan sonra değişirse `409` +
  `code: "COMMISSION_PRICING_CHANGED"` döner.
- Ürün fiyatı/kampanya veya kargo tarifesi değişirse mevcut
  `409 PRICING_CHANGED` davranışı sürer.
- Her iki `409` durumunda da yeni quote çek, güncel tutarı kullanıcıya göster ve
  ödeme onayını yeniden al. Eski snapshot ile sessiz otomatik retry yapma.
- Aktif/eşleşen komisyon kuralı yoksa `503` döner; bu yeniden quote ile çözülecek
  kullanıcı hatası değil, geçici platform yapılandırma hatasıdır.

### Kurumsal satış yetkisi

- `POST /cart/items` askıdaki satıcı ürünü için `409` +
  `code: "SELLER_SALES_SUSPENDED"` dönebilir.
- Public katalog ve ürün detayı, satış yetkisi olmayan satıcının ilanlarını gizler;
  daha önce açılmış detay `404` olabilir. Bu durumda bayat detayı satın alınabilir
  göstermeyip listeye dön.
- Kurumsal satıcının ilan oluşturma/düzenleme işlemi üyelik sona erdiyse kapalıdır;
  yalnız ilanı pasife alma yolu açık kalır. Mobil satıcıyı BUSINESS üyelik yenileme
  akışına yönlendirmeli.

## 2. İlan oluşturma ve düzenleme

### 2a. Araç modeli ve üretici model kodu artık opsiyonel

`POST /products`:

- `carModelId?: string` — göndermemek geçerlidir.
- `modelCode?: string` — göndermemek geçerlidir; varsa trimlenir, en fazla 100.
- `brandId` ve `manufacturerId` zorunlu kalır.

Formda model seçimi ve model kodu etiketindeki zorunluluk kaldırılmalı. Marka
değiştiğinde eski model seçimini temizleme kuralı sürer. `PATCH /products/:id`
ile modeli temizlemek için `carModelId: null`, model kodunu temizlemek için boş
veya yalnız boşluk içeren string gönderilebilir.

### 2b. Yeni ilan indirimli açılabilir

`POST /products` gövdesine opsiyonel alanlar eklendi:

```ts
originalPrice?: number | null;
salePrice?: number | null;
saleStartDate?: string | null; // ISO-8601
saleEndDate?: string | null;   // ISO-8601
```

`price`, formdaki indirim öncesi normal fiyattır. `salePrice > 0` ve
`salePrice < max(originalPrice, price)` ise sunucu ürünü indirimli oluşturur;
aksi halde indirim alanlarını yok sayar. Tarih aralığı dışındayken ürün normal
fiyattan satılır. Mobil toplamı veya etkin fiyatı kendisi türetmemeli; ürün/quote
yanıtındaki `price`, `oldPrice` ve `isOnSale` alanlarını esas almalı.

### 2c. Düzenleme formunun tek kaynağı: `edit`

`GET /products/my/:id` artık iki farklı projeksiyon döndürür:

- üst seviye alanlar: kullanıcıya gösterilecek ürün görünümü;
- `edit`: kayda geri yazılabilecek ham düzenleme değerleri.

Mobil form **yalnız `edit` bloğundan** doldurulmalı:

```ts
edit: {
  title: string | null;
  description: string | null;
  price: number | null;
  oldPrice: number | null;
  salePrice: number | null;
  saleStartDate: string | null;
  saleEndDate: string | null;
  categoryId: string | null;
  brandId: string | null;
  carModelId: string | null;
  manufacturerId: string | null;
  condition: string | null;
  status: string | null;
  modelCode: string | null;
  color: string | null;
  isBoxed: boolean | null;
  quantity: number | null;
  maxQuantityPerOrder: number | null;
  shippingPackageTier: "small" | "medium" | "large";
  isTradeEnabled: boolean;
  isSet: boolean;
  bundleSize: number | null;
  isLimited: boolean;
  editionNumber: string | null;
  editionTotal: number | null;
  releaseDate: string | null;
  year: number | null;
  images: Array<{
    cardKey: string;
    detailKey: string;
    cardUrl: string;
    detailUrl: string;
    sortOrder: number;
  }>;
  attributes: Array<{
    groupSlug: string;
    groupName: string | null;
    slug: string;
    value: string | null;
    displayValue: string | null;
    manufacturerSlug: string | null;
  }>;
}
```

Bu endpoint `Cache-Control: no-store` döner. Mobil de düzenleme kaydını kalıcı
cache'ten doldurmamalı; ekran açılışında güncel kaydı çekmeli.

İndirim formunu doldururken kanonik çift `edit.price` + `edit.oldPrice`'tır:
`oldPrice > price` ise formun normal fiyatı `oldPrice`, indirimli fiyatı
`price` olmalıdır. `edit.salePrice` geriye uyum alanıdır; tek başına otorite
olarak kullanılmamalıdır.

### 2d. Görsel listesi sahiplik ve sıra sözleşmesi

`POST /media/upload/product` yanıtındaki `cardKey`/`detailKey` değerleri artık
kullanıcının geçici yükleme klasörüne bağlıdır. İstemci key üretmemeli, URL'den
key çıkarmamalı ve başka bir ilanın key'ini yeni upload gibi kullanmamalı.

`POST /products` ve `PATCH /products/:id` için:

- `images[]` sırası kanoniktir; indeks `sortOrder` olur. Kapak ilk elemandır.
- Aynı key'in tekrarı reddedilir.
- Yeni key'in isteği yapan kullanıcıya ait upload'tan gelmesi gerekir.
- Düzenlemede mevcut ilana zaten bağlı eski key'ler korunabilir.
- Üyelik görsel üst sınırı create ve update'te uygulanır.
- Update'te `images` alanını göndermemek mevcut listeyi korur; göndermek listenin
  tamamını değiştirir; `[]` tüm görselleri temizler.
- Görsel yazımı ürün güncellemesiyle aynı transaction'dadır. `409`/iyimser kilit
  hatasında yerel formu sunucuda kaydedilmiş sayma; kaydı yeniden çekip kullanıcıya
  çakışmayı göster.

Mobil yükleme kuyruğu bitmeden kaydetmeyi açmamalı. Başarılı upload'ın geçici
önizleme URL'i yerine API'nin döndürdüğü `cardUrl/detailUrl` ve key çiftini saklamalı.

### 2e. İlanlarım işlem bağlamı

`GET /products/my` satırlarında sipariş/takas bağlamı artık açık alanlarla
gelebilir:

- `relatedOrder`: `id`, `orderNumber`, `status`, alıcı ve tutar özeti.
- `relatedTrade`: `id`, `tradeNumber`, `status`, `createdAt`.

Satılmış/rezerve ilan aksiyonunu tahmini bir `orderId` alanından veya son yerel
işlemden türetmek yerine bu alanlar varsa onları kullan.

## 3. Bildirim sözleşmesi ve deep link'ler ⚠️ P1

`09-messaging-notifications.md` içindeki “`type` serbest metindir, sunucuda enum
yok” bilgisi artık geçersizdir. Sunucuda kalıcı yazılabilen tipler kapalı
`NotificationType` enum'undadır. İstemci yine ileri uyumluluk için bilinmeyen
tipi genel kart olarak gösterebilir; fakat bilinen tiplerin route eşlemesi
güncellenmelidir.

Yeni enum değerleri:

```text
admin_broadcast
payment_confirmed, payment_failed, payment_refunded
trade_ready_for_shipping, trade_warehouse_approved,
trade_warehouse_rejected, trade_cancel_locked,
trade_return_completed, trade_return_lost,
trade_refund_failed, trade_refund_completed
```

Bildirim yanıtı yine şu şekildedir:

```ts
{ id, type, title, message, icon?, link?, isRead, createdAt, data? }
```

Fakat `link` artık tip + `data` üzerinden sunucuda merkezi olarak çözülür:

- Aynı tip alıcı ve satıcıya gidiyorsa `data.audience` (`buyer | seller`) doğru
  sipariş ekranını seçer.
- Dinamik ID parçaları URL-encode edilir.
- Zorunlu ID veya `audience` eksikse yanlış hedef üretmek yerine `link: null`
  dönebilir. Kart yine gösterilmeli; tıklama devre dışı bırakılabilir.
- Kampanya/yönetici gibi serbest hedefler yalnız `https://...` veya `/` ile
  başlayan site-içi yol olabilir. Mobil `javascript:`, özel scheme veya bilinmeyen
  host'u doğrudan açmamalı.
- `link` web route'udur; tek bir `toMobileRoute(type, link, data)` katmanında mobil
  route'a çevrilmeli. Ön plan, arka plan ve soğuk başlatma aynı resolver'ı kullanmalı.

Önemli hedefler:

| Tip grubu                          | Mobil hedef                                                   |
| ---------------------------------- | ------------------------------------------------------------- |
| `payment_confirmed`                | Sipariş detayı; `orderId` yoksa sipariş listesi               |
| `payment_failed`                   | İlgili sipariş/ödeme tekrar deneme ekranı                     |
| `payment_refunded`                 | `data.audience` tarafına göre alıcı veya satıcı siparişi      |
| `trade_*` yeni tipleri             | `data.tradeId` ile takas detayı; ID yoksa takas listesi       |
| `refund_*_seller`                  | Satıcı sipariş/iade görünümü                                  |
| `offer_received` / `offer_counter` | Gelen / gönderilen teklif sekmesi                             |
| `order_*` audience kullanan tipler | Alıcı için profil siparişi, satıcı için satıcı sipariş ekranı |

### Push token çıkış düzeltmesi

Mevcut `09` dokümanındaki `deactivate: true` alanı yanlıştır. DTO'nun güncel
alanı:

```json
{
  "token": "ExponentPushToken[...]",
  "platform": "ios",
  "deviceId": "...",
  "revoke": true
}
```

Çıkışta ve cihaz token'ı bırakılırken `revoke: true` gönderilmeli.

## 4. Sürat kargo: mobil akış değişikliği, yeni mobil endpoint yok

Kargo entegrasyonu yalnız resmi Sürat create ucu (`GonderiyiKargoyaGonder`, ya
da `SURAT_CREATE_API_VERSION=v2` ile `GonderiOlustur`) ve
`KargoTakipHareketDetayi` sağlayıcı uçlarıyla yeniden kurgulandı. Bunlar mobilin
doğrudan çağıracağı endpointler değildir; mobil yine Tarodan `/shipping` ve
`/orders` sözleşmesini kullanır.

### Sipariş kargosu

- Ödeme tamamlanınca backend shipment satırını otomatik oluşturmayı dener.
- Satıcı kargo ekranı önce `GET /shipping/order/:orderId` çağırmalı.
- Shipment varsa tekrar `POST /shipping` yapma; endpoint mevcut shipment için
  hata döndürür.
- Yalnız shipment `404` ise, sipariş `preparing` durumundaysa ve kullanıcı satıcıysa
  `POST /shipping` `{ orderId, provider: "surat" }` onarım yolu olarak kullanılabilir.
- Sipariş/grup iptali mevcut order endpointleri üzerinden yapılır. Mobil için
  taşıyıcı iptal endpointi yoktur; eklenen fiziksel taşıyıcı iptal operasyonları
  admin'e özeldir.

### Kodların anlamı

| Alan                 | Anlam                                                                           |
| -------------------- | ------------------------------------------------------------------------------- |
| `trackingNumber`     | Tarodan/Sürat sorgu referansı (`PKG-...` veya `ORD-...`); UI kargo kodu değil   |
| `providerTrackingId` | Gerçek Sürat `KargoTakipNo`; `/shipping` yanıtında kullanıcıya gösterilecek kod |
| `shipment.cargoCode` | Order/grup yanıtlarında `providerTrackingId` için kolaylaştırılmış alan         |
| `labelZpl`           | Resmi iki endpoint ZPL döndürmediğinden beklenmemeli                            |

Gönderi oluşturma başarılı olsa bile takip kaydı Sürat tarafında hemen görünmeyebilir.
Bu normal ara durum:

```text
status = pending
trackingNumber = PKG-... / ORD-...
providerTrackingId = null
```

Mobil “Kargo kodu hazırlanıyor” göstermeli; uygulama odağa geldiğinde, pull-to-refresh
ile veya makul aralıklı refetch ile gerçek kodu yenilemeli. `trackingNumber`'ı
Sürat takip sayfasına göndermemeli. Kod geldiğinde `providerTrackingId`/`cargoCode`
ile takip bağlantısını açmalı.

Kalıcı backend yaşam döngüsü için `docs/SHIPPING.md` günceldir.

## 5. Sözleşme değişmeyen ama davranışı netleşen alanlar

- `DELETE /membership/cards/:id` yanıtı değişmedi: başarılı silme `{ deleted: true }`.
  Kart yerelde hemen gizlenir, sağlayıcı temizliği backend outbox'ında yeniden denenir.
  Mobil başarılı yanıttan sonra listeyi invalidate etmelidir; PayTR temizliğini beklememeli.
- Ürün/satıcı puanları yalnız onaylı değerlendirmeleri sayar. Alan şekli değişmedi;
  mobil mevcut `rating.average/count` alanlarını göstermeye devam eder.
- Bull scheduler hata yayılımı, admin kargo iptali, ortam şablonları, e2e seedleri ve
  web yasal/içerik sayfaları mobil API sözleşmesi değildir.
